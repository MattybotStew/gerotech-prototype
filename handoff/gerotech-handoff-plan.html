Gerotech Website Redesign — Design-to-Development Handoff Plan

Prepared for: Project Management  |  Prepared by: CloudMellow (Matt)

Date: September 16, 2026  |  Status: Draft for review

1. Purpose

This document defines how we hand the approved HTML/CSS/JS prototype to WordPress development, and recommends the page-builder approach. It covers the current production site, the recommended theme strategy, the builder decision, the handoff deliverables, scope, phasing, and the decisions we still need.

2. Executive Summary

  • The new header and footer are global, theme-level elements — they will not be built in any page builder, regardless of which one we choose.
  • The live site currently runs a custom WordPress theme with no page builder at all; content is hardcoded in templates. We are not constrained by an existing builder.
  • We recommend a child theme of the current gerotech theme, with custom post types moved into a small companion plugin. This keeps changes isolated and gives us instant rollback.
  • On page builders, our recommendation is Gutenberg + ACF Blocks as the best fit for this bespoke design system, with WP Bakery as a strong second if the client or team prefers it. A short comparison is included; we propose finalising this before build.
  • Scope is the 11 prototype pages only — no migration of the existing 40+ live URLs at this stage.
  • Work proceeds in six phases, from freezing the prototype to page builds and QA.

The design system — not the builder — must remain the source of truth.

4. Recommended Approach

4.1 Theme Strategy

We recommend a child theme of the existing gerotech theme, plus one structural improvement:

  • Move custom post type registration into a small “Gerotech Core” plugin. Post types stored in a theme break when the theme changes; a plugin is the correct home and gives us a clean place for future custom fields.
  • The child theme owns the new header, footer, and page templates, loads the new design tokens and stylesheets in the documented order, and disables the old theme’s grid CSS and scripts.
  • The parent theme stays untouched, so we can roll back instantly if needed.

This is safer than editing the parent theme directly. We would only build a fully new theme if, on inspection of the staging copy, the parent proves unmaintainable. That inspection is the one remaining fork in the road.

4.2 Page Builder Decision

The header and footer are excluded from this decision — they live in the theme. The builder only governs page content. Our assessment against this project’s actual criteria:

Criterion WP Bakery Gutenberg + ACF Blocks Elementor
Fit with our custom design systemPoor unless we build custom elements; injects its own gridNative — markup stays oursPoor — heavy wrapper markup
Client editing experienceFamiliar, visualStructured fields + live preview; excellent when well builtFamiliar, visual
Shortcode / vendor lock-inHighNoneHigh
PerformanceAdds weightLightestHeaviest
Long-term maintenance (retainer)Builder + our CSS can conflictFewest moving partsMost moving parts
Compatibility with the classic themeExcellentExcellentGood

Recommendation: Gutenberg + ACF Blocks. It is the only option where the prototype’s design system survives intact, the client gets structured editing fields, and there is no shortcode lock-in on a site we will maintain for years.

WP Bakery is a defensible second choice — appropriate if the client already knows it or the team standardises on it. In that case we would build custom Gerotech elements, disable its default grid, and still keep header, footer, and structured content in the theme. We will include build-cost estimates for both so the trade-off is concrete.

5. Handoff Deliverables

A handoff/ package in the project repository:

  1. Builder decision document — the comparison above, finalised with costs.
  2. Component inventory — the core artifact: every section mapped to its code class, the pages it appears on, whether it is shared or page-specific, its editable fields, and its builder equivalent.
  3. Design tokens export — colours, spacing, type scale, fonts, breakpoints, radii.
  4. Header/footer specification — the new markup and behaviour as theme templates, including the decision on whether to keep the Megamenu plugin or rebuild the navigation.
  5. Content model — which sections are driven by structured content (galleries, testimonials, news) versus editable page fields, with the custom field definitions.
  6. Page template specifications — one sheet per page: section order, shared versus page-specific, editable fields.
  7. Interaction specification — slider, tabs, modals, search, sticky navigation, stat counter, gallery; including accessibility and motion-reduction behaviour.
  8. Asset manifest — final versus placeholder imagery, logos, icons, fonts, videos, and rights flags (notably the FANUC badge and Haas F1 lockup, both pending approval).
  9. Responsive and accessibility QA checklist — breakpoints, browser matrix, accessibility targets.
  10. Open decisions register — see Section 8.

6. Scope and Assumptions

In scope: the 11 prototype pages (Homepage, Engineered Solutions, Machine Custom Solutions, Automation & Controls, Applications, Training, Support, About, Careers, plus the Machine Modification redirect and the exploratory Showroom / Hero Variations pages as needed).

Out of scope: migration of the existing 40+ live URLs (training classes, service pages, people, careers detail pages). These are flagged for a later phase.

Assumptions:

  • We retain the existing theme, plugins, and hosting; this is a redesign, not a replatform.
  • The prototype’s content and imagery are largely final, with client photography and a few copy items still outstanding.
  • Retainer hours cover our build; the client requires editing rights and a straightforward editing experience.

8. Open Decisions and Client Inputs Needed

  1. Page builder — confirm Gutenberg + ACF Blocks or WP Bakery (decision document to follow).
  2. Navigation — keep the Megamenu plugin or rebuild the navigation in the theme?
  3. URL strategy — do the prototype pages replace the existing top-level URLs (for example /engineered-solutions/, /support/, /about/) or take new ones? This affects search visibility.
  4. Machine catalogue links — approximately 40 placeholder links pending the Haas catalogue structure.
  5. FANUC badge and Haas F1 lockup — usage rights still unconfirmed; both are placeholders.
  6. News page, social URLs, and email signup integration — outstanding from the client.
  7. Client photography — the prototype uses temporary stock imagery throughout; final assets are needed before launch.

9. Recommendation

Proceed with Phase 1 and Phase 2 immediately — freeze the prototype and inspect the staging theme — while the builder decision is finalised in parallel. Our recommendation is Gutenberg + ACF Blocks on a child theme, scoped to the 11 prototype pages.
