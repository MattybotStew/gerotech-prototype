Building the design before the approval

A repeatable method for design-to-build projects — using the Gerotech website redesign as the worked example.

Open (30s). This is a method deck, not a project recap. Gerotech is the example; the four threads on this slide are the method.

Frame the ask early: by the end we want agreement to reuse this on the next engagement.

The problem

We couldn't start designing.

  • The design phase was waiting on written sign-off that hadn't arrived.
  • The client presentation date was already fixed.
  • Waiting would have meant arriving with concepts — instead of something that actually worked.
The risk

The schedule risk wasn't the design itself. It was the wait.

Slide purpose: establish that this wasn't an aesthetic problem — it was a schedule problem.

Keep it short. Leadership has lived this: a gate blocks work, and the deadline doesn't move.

The idea

Build a working draft instead of waiting.

We built a clickable draft of the site — real pages, real structure, real behaviour — and used it to make the design tangible and reviewable.

Use it when

  • A sign-off gate is blocking progress
  • The deadline is fixed and close
  • The design is complex enough to need testing

Don't use it when

  • The underlying scope is still being decided
  • The audience needs strategy, not an artefact

Key point: we didn't skip the process — we built the next step's evidence early.

The "don't use it when" column is what makes this a decision rule rather than a boast. Say it out loud so the method isn't oversold.

What we built

A clickable site, in nine days.

  • Built by hand, with no website software in the way — fast to change, easy to review.
  • Honest placeholders wherever content wasn't confirmed. We never guessed and never faked.
  • Started at two pages; grew to the full site once the direction was approved.

Rule

Placeholders are a feature, not a failure. They show exactly where a decision is still owed.

Numbers: 9 days from first line to client-ready draft; the page count grew over the following months.

The placeholder point matters for leadership: placeholders make outstanding decisions visible instead of hiding them in assumptions.

Why it held together

One style guide, from the first day.

  • Colours, type and spacing were defined once, then reused everywhere.
  • Every page was assembled from the same building blocks — not designed in isolation.
  • Months of changes and new pages never broke the look, because the rules lived in one place.
Rule

Decide the rules once. After that, every page is a variation — not a new decision.

Why it matters commercially: a shared style guide is what makes page 12 as fast to build as page 2, and what keeps a client-facing design consistent as more people touch it.

Avoid the technical vocabulary. Say "shared style guide and building blocks."

The payoff

The draft became the blueprint.

  • Nothing was thrown away. The pages the client approved were the pages we built from.
  • The build team worked from a working reference, not a static picture.
  • Fewer handoff gaps — because what was approved and what was built were the same thing.
Rule

When the draft is the specification, approval and build can't drift apart.

The single most important slide. The prototype paid for itself twice: it moved the design forward while blocked, then it removed the ambiguity from the build.

Pause here. This is the argument for adopting the method.

Scaling up

From 2 pages to 12.

The method scaled — but the real work stopped being the design and became coordination.

  • More pages, more feedback, more changes in flight at once.
  • What strained wasn't quality. It was keeping everything and everyone in step.
  • So we formalised two things: one feedback channel, and one shared brief.

Transition slide. Sets up the next two mechanisms — the feedback loop and the shared brief.

Honest framing without blame: growth exposed a coordination gap, and we closed it with process.

Mechanism one

One place for feedback, tied to the exact spot.

  • Client notes were attached to the precise part of the design they referred to.
  • Every note became a tracked item with an owner — and was closed off one by one.
  • Nothing was lost in email threads or meeting recollections.
Rule

Feedback is only useful if it's tied to a place and has an owner.

Plain version: the client commented directly on the design, and each comment became a task we could tick off.

This is what kept a long review cycle from becoming an argument about what was agreed.

Mechanism two

AI assistants that don't forget.

Three plain documents let any assistant, on any day, pick up the work cold:

Instructions

How we work — the rules and standards, written once.

Current status

What's true right now: what's done, what's blocked, what's next.

Project diary

What happened and why, so decisions aren't re-litigated.

Rule

Shared memory is what turns many separate sessions into one continuous project.

Demystify it. These are three ordinary documents, not software. The point is that a new session — human or AI — starts informed instead of guessing.

Leadership takeaway: continuity is a process choice, not a technology feature.

Who did what

The right tool for each job.

  • Our AI assistants ran inside Cursor and VS Code.
  • Using Cline and opencode, powered by DeepSeek.
  • Each was used where it was strongest. People set direction and made every decision.
Rule

Tools are interchangeable. The shared brief is not.

Keep this slide factual and brief. Name the tools, then move the emphasis back to the method.

Pre-empt the obvious question: the tools changed during the project; the brief didn't. That's why continuity survived.

Choosing how to build it

We costed the options before committing.

  • Route A required rebuilding every custom section inside a page builder — estimated at 46–70 developer days, with ongoing lock-in.
  • Route B — the chosen path — was a custom layer on the existing site, with editing controls the client owns.
  • The decision was made on numbers and risk, not preference.
Rule

Cost the build path before it starts — and write the decision down.

This slide protects the team. It shows the expensive option was genuinely considered and rejected on evidence.

Keep the builder discussion high-level — the reasoning is what leadership needs, not the tooling.

Keeping design and build in step

One source of truth, with safety checks.

  • The design stayed the single source of truth until the build was ready to take over.
  • Safe, repeatable steps moved approved changes across — and a comparison check proved nothing drifted.
  • A planned handover point transferred ownership cleanly, with no ambiguity about which copy wins.
Rule

Two copies of the truth is one too many. Name the winner, and check for drift.

Plain version: we agreed which copy was authoritative at each stage, and verified it automatically rather than trusting memory.

This is the discipline that prevented "it looked right on our screen" conversations.

Six days, start to finish.

Result

14 pages live and verified — every page returning correctly, with no errors.

Speed came from preparation, not shortcuts. The design was already a working reference, so the build was translation rather than invention.

The playbook

Eight rules worth reusing.

  1. When a gate blocks progress, build the working draft.
  2. Placeholders are a feature — they expose open decisions.
  3. Decide the rules once; every page after that is a variation.
  4. If the draft is the spec, approval and build can't drift.
  5. Tie every piece of feedback to a place and an owner.
  6. Give every session shared memory.
  7. Cost the build path before committing to it.
  8. A fix isn't done until it's verified automatically.

This is the slide to keep. Everything before it is justification; everything after is next steps.

Read them aloud slowly — these are the eight sentences we want people to leave with.

What's next

Two things we'd like to agree today.

Adopt the method

Use the shared-brief approach — instructions, status, diary — as the default on the next project.

Fund the verification step

Make automated checks standard, so silent problems can't reach a client-facing site.

Still open

Launch settings for the live domain, design direction for the remaining older pages, and a short list of client decisions.

Close on an ask, not a summary. Two decisions: adopt the method, and fund verification.

The "still open" items are deliberately brief — enough to show nothing is hidden, without turning the close into a risk review.
