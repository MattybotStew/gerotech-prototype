How to run a prototype-first build

Nine steps, taken from a real project — Gerotech's website redesign. Each step shows what to do, what it looks like, and how you know it worked.

Step 1 of 9

Start the working draft.

How to do it

  • Build the two or three pages that carry the decision first — not the whole site.
  • Build by hand, with no website software in the way, so changes take minutes.
  • Use honest placeholders wherever content isn't confirmed. Never guess, and never fake.
  • Keep it clickable: real navigation, real behaviour, real mobile layout.
How you know it worked

The client reviews a page instead of a picture — and the conversation moves to specifics.

Step 1 in one line: when the gate is closed, build the thing behind it.

Nine days from first line to client-ready. The placeholder habit matters — placeholders make outstanding decisions visible instead of hiding them in assumptions.

Step 1 · continued

Then go wide — cover the real pages.

How to do it

  • Once direction is approved, build every page in the same system.
  • New pages should be variations, not new decisions — that's what keeps page 12 cheap.
  • Test small screens as you go. Retrofitting mobile at the end always costs more.
  • Use the real imagery as soon as the client sends it. Stand-ins are for the gaps.
How you know it worked

Twelve pages, one system — and no page looks like a one-off.

Why "go wide" matters commercially: a shared style guide is what makes the tenth page as fast to build as the second — and what keeps the design consistent as more people touch it.

Step 2: decide the rules once, then every page is a variation.

Avoid systems vocabulary out loud. Say: "we decided the rules once." Point at the colour swatches — this is the file that stops page 12 drifting from page 2.

Step 3: client notes attach to the exact spot in the design, and each becomes a tracked item with an owner.

These are real comments from the design file. The point: a long review cycle never turns into an argument about what was agreed.

Step 4: three ordinary documents — not software. Instructions (how we work), current status (what's true now), project diary (what happened and why).

They're what let any session — a person or an assistant — start informed instead of guessing. Continuity is a process choice, not a technology feature.

Step 5 — the most important step. The page the client approved is the page that got built.

Say the line: "when the draft is the specification, approval and build can't drift apart." Pause here.

Step 6 of 9

Cost the build path before you commit.

Route A · rejected

Rebuild every section in a page builder

46–70 days

Every custom section rebuilt as a builder element, with ongoing lock-in and a permanent fight with its grid.

Route B · chosen

A custom layer on the existing site

6 days

The design system stays the source of truth, the client owns plain-language editing controls, and the parent site is untouched — so rollback is instant.

Rule

Put both routes on one page, in days and risk, before anyone starts building. Write the decision down.

This slide protects the team. It shows the expensive option was genuinely costed and rejected on evidence, not preference.

Keep the tooling detail out of it. Leadership needs the reasoning and the number, not the technology.

Step 7 of 9

Build from the draft.

How to do it

  • Work from the approved draft, not from a static picture or a memory of a meeting.
  • Reuse the same style guide — the build should be translation, not redesign.
  • Publish to a test site first, and compare it against the draft page by page.
  • Change only what the client asked to change. Everything else is already approved.
How you know it worked

Speed comes from preparation. 14 pages live and verified, with no redesign in the build phase.

Step 7: the build is translation, not invention. Six days start to finish, because the design was already a working reference.

If someone asks how you know the built page matched, open step 5 (the side-by-side) — it's the same argument.

Step 8: the client edits their own content without calling us.

Two habits make it usable: labels written in plain language, and the safe default stated inside the field. If a decision is still owed, leave the field empty rather than guessing.

Step 9 — the rule that prevents the worst failure: a control can render the design correctly while being empty in the admin. Nothing looks broken.

This is real output from the project's audit script: 279 of 291 controls applied. The remaining 12 are correct — a blank colour choice means "keep the design colour".

One page to keep

The checklist.

  1. Build the 2–3 pages that carry the decision, before approval lands.
  2. Decide colours, type and spacing once — then reuse them.
  3. Tie every client note to a spot in the design and an owner.
  4. Write the brief down: instructions, status, diary.
  5. Treat the approved draft as the specification.
  6. Cost both build routes in days and risk before committing.
  7. Build by translation; compare each page to the draft.
  8. Write editing labels in plain language, with the default stated.
  9. Automate the check — never verify by eye.

This is the slide to keep. Everything before it is justification; everything after is next steps.

Watch out for these · prioritised by impact

The roadblocks, and the fixes.

RoadblockWhy it mattersThe fix we now applyStatus
Editing controls looked empty while the site looked right The client couldn't update their own content — and nothing appeared broken 1. Every control is verified automatically Fixed
A routine save in the admin wiped chosen colours The approved design drifted with no warning 1. Risky defaults removed; blank means "leave as designed" Fixed
Changing the design didn't change the live page Two copies of the truth 1. One rule — saved content wins — applied with safe, repeatable fixes Fixed
The test site drifted from what was approved An unreviewed change could have gone live 2. Save to the project before publishing; compare file by file Fixed
A live older page looked like a duplicate We nearly removed a page the client still uses 2. Compare full web addresses, never just page names Prevented
Context lost between sessions Work had to be rebuilt from scratch each time 3. The shared brief — instructions, status, diary Fixed
Some fonts quietly fell back to a default Inconsistent typography across pages 3. Audited which fonts were actually loading Fixed

Priority key: 1 = could have blocked the client from editing, or damaged the approved design. 3 = friction. Every row leads with the fix and shows the status.

The two "silent" roadblocks are the most valuable lesson — they looked fine on screen. That's why step 9 exists.

Reusable

What made it fast

Preparation, not shortcuts. The design was already a working reference, so the build was translation rather than invention.

What made it safe

One source of truth at every stage, plus checks that ran themselves instead of relying on someone noticing.
