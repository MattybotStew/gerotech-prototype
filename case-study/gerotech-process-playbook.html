Internal process playbook

From kickoff call to a dev-ready build

We take a website from discovery to a fully designed, fully editable front end — designing in code rather than static files, then converting that prototype into WordPress without a page builder or a commercial theme.

Use it when

The design is bespoke enough that a page builder would fight it, the client needs to edit their own content, and the project will grow after launch.

Walk the eight phases — one line each. This is the map; the rest of the deck is the detail.

Phases 1–3 are the ones teams skip when they're in a hurry. Skipping them is what makes phases 4–6 expensive.

Phase 1. We audited the live site before designing anything, so the redesign was grounded in facts.

The finding that shaped everything: the client could not edit their own page content. That became a hard requirement for the build.

Note the last point on the right — inventory content that wasn't in the new structure was flagged for a client decision rather than silently dropped.

Phase 2. The structure is agreed before any design work, when changing it is free.

One decision here gets reused everywhere — navigation, mega-menu, mobile menu, breadcrumbs, search. That's why the same heading sits in the same place on all twelve pages.

Phase 3. Structure before style. Copy and section order get settled while changes are still cheap.

The wireframe carries forward: every section in it becomes a section in the built page, in the same order.

Phase 4 of 8 · the headline idea

Design happens in code, not in a static file.

How it works

  • We build the design as a working front end — real layout, real type, real breakpoints.
  • The client reviews a page they can scroll and click, not an image.
  • Feedback becomes a change we make in minutes, not a redraw and a re-export.
  • Nothing is thrown away — this becomes the build.
Why it matters

The design starts behaving like the finished thing on day one, so the conversation moves from taste to specifics.

This is the differentiator. Say it plainly: the design is not a picture of a website, it is the website.

Every objection you'd normally hear later — "that spacing looks different on my screen", "how does it behave on mobile" — is answered live.

Phase 4 · continued

Every page, not just the homepage.

How it works

  • New pages are variations on the same system, not new decisions — so page twelve costs a fraction of page two.
  • Responsive is built as we go. Retrofitting mobile at the end always costs more.
  • Real imagery goes in as soon as the client sends it; placeholders mark the gaps.
The result

Twelve designed pages, one system — and no page looks like a one-off.

The commercial point: a shared style guide is what makes the tenth page as fast as the second.

Phase 5. The design file doesn't get abandoned — it stays in step with the code, and changes flow both directions.

In practice this is driven from the editor: an AI assistant working against the shared brief makes the change in code, and the design file is updated to match what was approved.

Why keep both: the client and their stakeholders are comfortable reviewing in the design file, while the code is the thing that actually ships.

Phase 6. One feedback channel: notes attach to the exact spot in the design, and each becomes a tracked item with an owner.

Real comments from the Gerotech design file. The benefit: a long review cycle never turns into an argument about what was agreed.

Runs across every phase. Decide the rules once — colour, type, spacing — then every page is a variation.

Avoid systems vocabulary out loud. Say "we decided the rules once". This is the file that stops page twelve drifting from page two.

Runs across every phase. Three ordinary documents — not software. Instructions (how we work), current status (what's true now), project diary (what happened and why).

This is what lets several people and several AI assistants work on one project without losing state. Continuity is a process choice, not a technology feature.

Phase 7 — the payoff. Because the design was already working code, conversion is translation rather than reconstruction. The page the client approved is the page that ships.

Technically: WordPress's native editor plus structured fields, on a child theme. No page builder in the middle.

What the client gets. They edit their own content without calling us. Two habits make it usable: labels in plain language, and the safe default stated inside the field.

291 content controls across the site. If a decision is still owed, the field is left empty rather than guessed.

Phase 8 of 8

What development receives.

Already done

  • Every page designed and built, responsive, and verified against the approved draft.
  • The whole design system — colour, type, spacing and components — in version control.
  • Editing controls the client already owns, so content work isn't blocked on dev.
What dev adds

The complex functionality clients actually need — integrations, dynamic data, quoting flows, CRM and ERP connections — on top of a front end that already works.

Phase 8. Dev doesn't start from a static mockup and a blank template. They start from working pages and add the hard parts.

This is the sentence to land: we pass to dev a fully designed front end that is ready for the more complex functionality our clients need.

The payoff

What the client doesn't pay for.

Not needed

Page-builder licence

A builder would fight a bespoke design system, add lock-in, and cost more to maintain. We don't use one.

Not needed

Commercial theme licence

No purchased theme, and no annual renewal for one. The front end is ours, and it's in version control.

One licence

Advanced Custom Fields

A single plugin licence replaces both — and it's what gives the client structured, plain-language editing.

And they still get

A fully editable front end they can update themselves, on a site that stays maintainable for years.

Be precise here — it's the claim most likely to be challenged. We are not saying "zero licences". We are saying: no page-builder licence, no commercial theme licence, and one plugin licence covers both jobs.

If asked about the parent theme: the build is a child theme of the client's existing bespoke theme, so there is no purchased theme and no renewal. A block theme would remove that dependency entirely — that's the next step, not something we've shipped.

The rule that prevents the worst failure: a control can render the design perfectly while being empty in the admin. Nothing looks broken — which is why it gets missed.

This is real output from the audit script: 279 of 291 controls applied. The remaining 12 are correct by design — a blank colour choice means "keep the design colour".

One page to keep

The checklist.

  1. Audit what exists before designing anything.
  2. Agree the sitemap while changing it is free.
  3. Settle structure and content in wireframes.
  4. Design in code, so the design behaves like the site.
  5. Keep the design file and the code in step.
  6. One feedback channel, tied to a spot and an owner.
  7. Convert to the native editor plus structured fields — no builder.
  8. Leave the client editing controls they actually understand.
  9. Hand dev a working front end, not a mockup.

The slide to keep. Everything before it is justification; everything after is next steps.

Watch out for these · prioritised by impact

The roadblocks, and the fixes.

RoadblockWhy it mattersThe fix we now applyStatus
Editing controls looked empty while the site looked right The client couldn't update their own content — and nothing appeared broken 1. Every control is verified automatically Fixed
A routine save in the admin wiped chosen colours The approved design drifted with no warning 1. Risky defaults removed; blank means "leave as designed" Fixed
Changing the design didn't change the live page Two copies of the truth 1. One rule — saved content wins — applied with safe, repeatable fixes Fixed
The test site drifted from what was approved An unreviewed change could have gone live 2. Save to the project before publishing; compare file by file Fixed
A live older page looked like a duplicate We nearly removed a page the client still uses 2. Compare full web addresses, never just page names Prevented
Context lost between sessions Work had to be rebuilt from scratch each time 3. The shared brief — instructions, status, diary Fixed
Some fonts quietly fell back to a default Inconsistent typography across pages 3. Audited which fonts were actually loading Fixed

Priority key: 1 = could have blocked the client from editing, or damaged the approved design. 3 = friction. Every row leads with the fix.

The two "silent" roadblocks are the most instructive — they looked fine on screen. That's why the automated check exists.
